# /skill-review — 점검 단계

설계 문서와 구현 결과물을 3회 점검한다. 각 회차는 초점이 다르며 순서대로 진행한다.
점검은 계획 보고 없이 바로 실행한다 (자동화된 체크리스트 기반).

```
1차: 문서 완성도
2차: 전체 구조 파악 및 안전성
3차: 엣지케이스 + 보완 + 오류 발생 확인
```

사용법:
- `/skill-review 1` — 1차 점검
- `/skill-review 2` — 2차 점검
- `/skill-review 3` — 3차 점검
- `/skill-review` — 현재 상태에서 적절한 회차 판단 후 실행

---

## 1차 점검: 문서 완성도 + 기능 완성도

### 목적
기획서와 설계 문서가 충분히 채워져 있는가(문서 완성도),
그리고 기획한 기능이 설계에 빠짐없이 반영됐는가(기능 완성도)를 함께 확인한다.
구현 전에 빈 칸, 모호한 항목, 누락된 기능을 모두 잡아낸다.

### 체크리스트

#### A. 문서 완성도

**기획서 (docs/skill-brief.md)**
- [ ] 목적이 한 줄로 명확히 서술됨
- [ ] 입력 / 출력 / 트리거가 구체적으로 정의됨
- [ ] 스킬 경계 ("하지 않는 것")가 명시됨
- [ ] 성공 기준이 측정 가능한 형태로 작성됨

**CLAUDE.md**
- [ ] 기술 스택이 전부 나열됨
- [ ] CRITICAL 규칙이 최소 2개 이상 명시됨
- [ ] 빌드 / 테스트 / 배포 커맨드 기재됨 (없으면 "없음" 명시)
- [ ] `{{placeholder}}` 토큰이 남아 있지 않음

**docs/PRD.md**
- [ ] 기능이 F1부터 번호로 구분됨
- [ ] 각 기능마다 정상 시나리오가 있음
- [ ] 엣지케이스 테이블이 최소 기능당 3행 이상
- [ ] 에러 처리 테이블이 존재함
- [ ] `{{placeholder}}` 토큰이 남아 있지 않음

**docs/ARCHITECTURE.md**
- [ ] 디렉토리 구조가 실제 파일 트리 형태로 표시됨
- [ ] 데이터 모델 (엔티티 / 필드 / 타입) 테이블 존재
- [ ] 데이터 흐름 다이어그램 또는 순서 설명 존재
- [ ] `{{placeholder}}` 토큰이 남아 있지 않음

**docs/ADR.md**
- [ ] 최소 ADR-001이 작성됨
- [ ] 각 ADR에 결정 / 이유 / 트레이드오프 / 대안 검토가 모두 있음
- [ ] `{{placeholder}}` 토큰이 남아 있지 않음

**phases/ (Step 파일)**
- [ ] index.json에 phase가 1개 이상 등록됨
- [ ] 각 step 파일에 목표 / 구현 지시 / Acceptance Criteria가 있음

#### B. 기능 완성도

기획서(skill-brief.md)의 기능 목록과 설계 문서를 대조한다.

**PRD 반영 여부**
- [ ] skill-brief.md에 정의된 모든 기능이 PRD.md에 F번호로 등록됨
- [ ] 기획서의 성공 기준이 PRD의 Acceptance Criteria에 반영됨
- [ ] 기획서의 "하지 않는 것(경계)"이 PRD의 제약사항 또는 에러 처리에 명시됨

**ARCHITECTURE 반영 여부**
- [ ] PRD의 각 기능(F1, F2 ...)에 대응하는 모듈/레이어가 ARCHITECTURE에 존재함
- [ ] 데이터 흐름이 모든 기능의 입력→처리→출력을 커버함

**Step 반영 여부**
- [ ] PRD의 모든 기능이 최소 1개 이상의 Step에 구현 지시로 포함됨
- [ ] 어떤 기능도 Step 목록에서 누락되지 않음
- [ ] Step의 AC(Acceptance Criteria)가 해당 기능의 성공 기준을 직접 검증함

### 자동 확인
```bash

```

## 2차 점검: 전체 구조 파악 및 안전성

### 목적
문서 간 일관성, 기술 결정의 충돌, 실행 시 위험 요소를 확인한다.

### 체크리스트

**문서 간 일관성**
- [ ] PRD의 기능명과 ARCHITECTURE의 모듈명이 일치함
- [ ] ADR의 기술 결정이 CLAUDE.md의 기술 스택과 충돌하지 않음
- [ ] Step 파일의 순서가 ARCHITECTURE의 데이터 흐름 순서와 일치함
- [ ] PRD의 에러 처리가 ARCHITECTURE에서 해당 레이어에 반영됨

**안전성 확인**
- [ ] CLAUDE.md의 CRITICAL 규칙 중 각 Step이 위반하는 항목 없음
- [ ] 데이터 삭제 / 덮어쓰기 / 외부 API 호출이 있다면 ADR에 근거가 있음
- [ ] LockService, 트랜잭션, 동시성 이슈가 있다면 처리 방법이 명시됨
- [ ] 원본 데이터 수정 위험이 있는 Step에 읽기 전용 제약이 명시됨

**Step 실행 안전성**
- [ ] 각 Step이 이전 Step의 결과 없이 단독 실행 시 오류 처리 있음
- [ ] 실패 시 재시도 가능한 구조인가 (부분 실행 후 중단해도 안전한가)
- [ ] 최대 파일 크기 800줄 규칙을 각 Step이 준수하는가

**외부 의존성**
- [ ] 외부 API, 서드파티 라이브러리가 ADR에 선택 근거가 있음
- [ ] 네트워크 없이도 로컬 테스트 가능한가 (불가능하면 명시)

### 보고 형식
```
## 2차 점검 결과

**문서 간 충돌:**
- [충돌 항목] — [수정 방향]

**안전성 위험:**
- [위험 항목] — [대응 방법]

**수정 필요 문서:**
- [파일명]: [수정 내용]

판정: 통과 / 수정 후 재점검 필요
```

## 3차 점검: 엣지케이스 + 보완 + 오류 발생 확인

### 목적
실제 사용 시 발생 가능한 예외 상황, 누락된 처리, 잠재적 오류를 모두 잡아낸다.
이 단계가 통과되면 구현 단계로 진행한다.

### 체크리스트

**엣지케이스 충분성**
- [ ] 입력이 비어 있거나 null인 경우 처리됨
- [ ] 입력이 예상 형식과 다른 경우 처리됨
- [ ] 데이터가 0건 / 1건 / 대용량인 경우 모두 처리됨
- [ ] 권한 없는 사용자 접근 시 처리됨
- [ ] 네트워크 / 외부 서비스 장애 시 처리됨
- [ ] 동시 실행 / 중복 호출 시 처리됨

**누락 확인**
- [ ] PRD에 기획서의 모든 기능이 반영됨
- [ ] ARCHITECTURE에 PRD의 모든 기능에 대응하는 모듈이 있음
- [ ] 각 Step의 Acceptance Criteria가 PRD의 성공 기준을 커버함
- [ ] ADR이 설계 중 내린 모든 주요 결정을 기록함

**잠재 오류**
- [ ] 6분 실행 제한 초과 가능한 루프/배치가 BatchRunner로 처리됨 (GAS인 경우)
- [ ] 대용량 데이터에서 CacheService 100KB 제한 초과 가능성 검토됨 (GAS인 경우)
- [ ] 타입 불일치, null 참조, 배열 범위 초과 가능한 코드 경로 없음
- [ ] 에러 발생 시 사용자에게 명확한 메시지가 전달됨 (에러 코드만 노출 금지)

**보완 항목 확인**
- [ ] 1차 점검에서 지적된 항목이 모두 수정됨
- [ ] 2차 점검에서 지적된 항목이 모두 수정됨
- [ ] 수정으로 인해 새롭게 생긴 충돌이 없음

### 최종 자동 확인
```bash
# placeholder 완전 제거 확인
grep -rE '\{\{[^}]+\}\}' . --include="*.md" --include="*.json" \
  | grep -v "SKILL.md" | grep -v "commands/"

# step 파일 존재 확인
ls phases/0-mvp/step*.md

# index.json 유효성
python3 -c "import json; json.load(open('phases/0-mvp/index.json')); print('JSON valid')"
```

**엣지케이스 누락:**

**잠재 오류:**

## 판정 기준

| 판정 | 조건 | 다음 행동 |
|------|------|----------|
| 통과 | 모든 체크 통과, placeholder 0개 | 다음 회차 또는 /skill-build |
| 보완 필요 | 미통과 항목 1~3개 | 수정 후 동일 회차 재점검 |
| 재설계 필요 | 구조적 충돌 또는 5개 이상 미통과 | /skill-design 으로 돌아감 |
