## 불일치 #1: Theology Filter 구현 방식

**충돌 지점**
- t1 Branch 1.2: Hook 조건 분기 한계 → 복잡한 신학 판단은 **프롬프트 에이전트에 위임**
- t2 Branch 2.2: 전용 theology_guard.py Hook으로 **신학 판단 격리**

**충돌 원인**
- t1은 Hook 기능의 기술적 한계(단순 regex만 가능)를 근거로 프롬프트 위임 주장
- t2는 독립성과 신뢰성을 근거로 Hook 격리 주장

**해결**
- 2중 방어 채택: **1차 방어 = 프롬프트** (복잡한 신학 판단), **2차 방어 = Hook** (단순 금지 키워드 차단)
- Hook은 regex 수준의 단순 패턴만 담당. 신학적 판단은 Theology Filter 에이전트가 담당.

## 불일치 #2: 병렬 오케스트레이션 도입 시점

**충돌 지점**
- t3 Branch 3.2 (고도): 병렬 Task 즉시 도입 권장
- t3 Branch 3.1 (경량): Phase 2 이후 점진 도입 권장
- t1 Branch 1.2: 병렬 Task 수 상한 미명시 → 실험적 위험

**충돌 원인**
- 실행 시간 단축(고도) vs 안정성(경량) 간 가치 충돌
- 기존 rate limit 실패 사례(SaaS-AgenticWorkflow)가 경량 측 근거

**해결**
- Phase 1 MVP = 경량 순차 (필수)
- Phase 2 = 3개 파이프라인 안정화 후 병렬 Task 도입
- 단, 설정 아키텍처(t2)는 Phase 1부터 병렬 지원 구조로 설계
