## Branch A: Claude Code 단독 완결 전제 시나리오

### 3개 핵심 파이프라인 실제 흐름

| 파이프라인 | 단계 순서 | 산출물 형태 |
|-----------|----------|------------|
| **설교** | 본문입력 → 주석분석(Exegesis) → FCF도출 → 설교구조(Structure) → 신학필터(Filter) → 적용(Application) → 설교문 초안 | sermon-draft.md |
| **양육** | 대상분석(Learner) → 커리큘럼 설계(Curriculum) → 콘텐츠 생성(Content) → 교육필터(Education Filter) → 레슨자료 | lesson.md |
| **행정** | 요청분류(Operations) → 문서생성 → 검토 → 최종문서 | doc-output.md |

### 시나리오 우선순위
- **가장 빈번한 시나리오**: 주일설교 준비 (매주 필수, 대체 불가)
- **가장 가치 높은 시나리오**: 설교 파이프라인 (시간 절감 최대, 핵심 사역)
- **가장 구현 어려운 시나리오**: 양육 커리큘럼 (학습자 분석 데이터 없으면 일반화됨, 컨텍스트 요구량 큼)

### 대안 도구 조사 (로컬 실행 가능 여부 포함)
| 도구 | 강점 | 약점 | 로컬 실행 |
|------|------|------|----------|
| weekly-works(didim) | 설교·묵상 파이프라인 이미 구현 | 신학 필터 없음, 멀티에이전트 아님 | ✅ 로컬 |
| 수동 ChatGPT | 즉시 사용 | 신학 일관성 없음, 자동화 없음 | ❌ 클라우드 |
| n8n (로컬) | 파이프라인 자동화 | 신학 도메인 없음, 설정 복잡 | ✅ 로컬 (설치 필요) |

### Branch A 결론

- 3순위: 양육 커리큘럼 (Phase 2)

## Branch B: 외부 연동 전제 관점

### 핵심 발견 — weekly-works(didim) 중복 문제
- `weekly-works` 시스템이 이미 로컬에서 설교·묵상·기도회 파이프라인을 구현하고 있음
- 이 시스템(AI 교역자팀)이 didim과 **다른 점**: 신학 필터 + 멀티에이전트 구조
- 이것이 실제 차별점인지, 아니면 중복인지 확인 필요

### 중복 가능성 분석
| 기능 | weekly-works(didim) | AI 교역자팀 |
|------|---------------------|------------|
| 설교 준비 | ✅ sermon 에이전트 | ✅ Sermon Pipeline |
| 묵상 생성 | ✅ weekly-devotion | ❌ 없음 |
| 신학 필터 | ❌ 없음 | ✅ Theology Filter |
| 멀티에이전트 구조 | 부분적 | ✅ 완전 구현 |
| 행정 자동화 | ❌ 없음 | ✅ Operations |

### Branch B 결론
- didim 없는 기능(신학 필터, 행정, 전략)을 이 시스템의 핵심으로 삼아야 중복을 피함
- 설교 파이프라인은 didim 위에 신학 필터 레이어를 추가하는 방식 검토 필요

### 파킹 로트
- weekly-works(didim)와 이 시스템의 역할 경계 정의 — **구조적 리스크 카테고리**
  - PRD 작성 전 선결 과제: 이 정의가 없으면 파이프라인 범위가 두 번 흔들림
  - 발견 Branch: B
- 산출물 형식 결정 (md vs HTML vs docx)
  - didim이 이미 HTML A4 캡처까지 하므로 중복 여부 확인 필요
  - 카테고리: 구조적 리스크
