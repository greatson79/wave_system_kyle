## Branch A: 파워 유저 — 목사 + 보조 스태프

### 페르소나 상세
- **배경**: 담임목사, 비개발자, Claude Code 사용 경험 있음
- **현재 작업 방식**: 설교 준비 수동(6~8시간/주), 행정 문서 수동 작성
- **핵심 불편함**: 반복적 구조 생성 (FCF, CMT, 3포인트 설교) / 원어 조사 시간

### 수용 가능한 복잡도
- **수용 가능**: 슬래시 커맨드(`/설교 [본문]`)로 시작 → 결과 받기
- **수용 불가**: `.claude/agents/*.md` 직접 편집, Python 스크립트 설치, YAML 수동 수정
- **디버깅**: 에러 발생 시 자체 해결 능력 없음 → 시스템이 명확한 오류 메시지를 한국어로 제공해야 함

### 사용자 여정 마찰 지점
| 단계 | 마찰 지점 | 이탈 위험 |
|------|----------|----------|
| 설치 | Hook, agents 디렉터리, state.yaml 수동 설치 | 매우 높음 |
| 초기 설정 | CLAUDE.md 편집 | 높음 |
| 첫 실행 | 슬래시 커맨드 존재 모름 | 중간 |
| 반복 사용 | 결과 품질 일관성 없으면 신뢰 손상 | 높음 |
| Theology Filter FAIL | 다음 행동을 모름 | 높음 |

### 이탈 위험 최고 지점
**초기 설치·설정 단계**: Hooks, agents 디렉터리, state.yaml을 수동 설치해야 한다면 목사는 시작조차 못함.

### 필수 구성요소 (파워 유저 관점)
1. `/install` 자동 설정 커맨드 (설치 복잡도 제거)
2. 슬래시 커맨드 인터페이스 (`/설교`, `/양육`, `/행정`)
3. 한국어 출력 (모든 에이전트 산출물)
4. Theology Filter FAIL 시 human-in-the-loop 명확한 안내

### 파킹 로트
- Theology Filter PASS/FAIL 시 목사에게 어떤 형태로 결과를 전달할 것인가
  - 카테고리: 사용자 행동 가설 검증
- 스태프(교육부, 행정) 별도 접근 방식 설계
  - 카테고리: 사용자 행동 가설 검증 (Phase 2)

## Branch B: 일반 사용자 — 단순 자동화 원하는 스태프

### 페르소나 상세
- **배경**: 교회 스태프(교육·행정 담당), 비개발자
- **핵심 불편함**: 반복 문서 작성, 커리큘럼 초안 작업
- **수용 가능한 복잡도**: 미리 설정된 템플릿에서 선택하는 수준

### Branch B 결론
- Operations Agent, Curriculum Agent만 필요한 경우 전체 12개 에이전트 시스템은 과도함
- 스태프용 경량 인터페이스 별도 설계 필요 (Phase 2)

### 파킹 로트
- 멀티 사용자(스태프 팀) 지원 시 설정 공유 방식
  - 카테고리: 사용자 행동 가설 검증
  - Phase 2 이후 검토

## Branch A vs B 비교 정리

| 항목 | Branch A (목사) | Branch B (스태프) |
|------|----------------|-----------------|
| 우선 대상 | 담임목사 1인 | 스태프 팀 |
| 인터페이스 | 슬래시 커맨드 | 템플릿 선택 |
| 복잡도 수용 | 낮음 | 매우 낮음 |
| Phase 1 포함 | ✅ | ❌ (Phase 2) |

### 결론 (Operator Analyst)
**담임목사 1인 중심 설계**가 Phase 1 우선. 슬래시 커맨드 기반, `/install` 자동 설치, 한국어 출력, Theology Filter FAIL 시 명확한 안내가 없으면 실제 사용 불가. 스태프 확장은 Phase 2.

### 미해결 / 후속 조사 필요
- `/install` 커맨드 구현 시 포함할 자동화 항목 목록
- Theology Filter FAIL 시 사용자에게 전달할 메시지 형식
