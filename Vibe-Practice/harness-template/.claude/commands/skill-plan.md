# /skill-plan — 기획 단계

스킬 제작의 첫 번째 단계. 사용자의 의도를 구조화하고 기획서를 작성한다.
실행 전 반드시 **기획 계획을 먼저 보고**한 뒤 승인을 받아 진행한다.

---

## Step 1: 기획 계획 보고 (실행 전 필수)

아래 형식으로 보고한 뒤 사용자 승인을 기다린다. 승인 없이 문서 작성으로 넘어가지 않는다.

```
## 기획 계획 보고

**스킬명 (가안):** [사용자 입력 기반]
**파악한 목적:** [한 줄 요약]

**기획 인터뷰 순서:**
1. 스킬이 해결하는 문제
2. 입력 / 출력 / 트리거
3. 스킬의 경계 (하지 않는 것)
4. 성공 기준
5. 유사 스킬과의 차별점

**산출물:** `docs/skill-brief.md` 생성 (프로젝트 루트 기준)

승인하시면 인터뷰를 시작합니다.
```

---

## Step 2: 기획 인터뷰

승인 후 아래 질문을 순서대로 진행한다. 한 번에 몰아서 묻지 않고 답변을 받으며 이어간다.

### Q1. 이 스킬은 무엇을 하는가?
```
- 어떤 문제를 해결하는가 (지금 불편하거나 반복하는 것):
- 사용자가 주는 것 (입력):
- 스킬이 만들어내는 것 (출력):
- 언제 이 스킬을 부르는가, 커맨드명:
```

### Q2. 하지 않는 것과 "다 됐다"는 걸 어떻게 아는가?
```
- 이 스킬이 절대 하지 않는 것:
- 다 됐을 때 눈에 보이는 결과 (파일 생성 / 화면 출력 / 테스트 통과 등):
- 사람이 직접 확인해야 하는 것:
```

### Q3. 참고할 것이 있는가?
```
- 비슷한 기존 스킬이나 도구:
- 참고할 문서나 패턴 (없으면 생략):
```

---

## Step 3: 기획서 작성

인터뷰 완료 후 `docs/skill-brief.md`를 생성한다.

```markdown
# 스킬 기획서: [스킬명]

## 요약
- **목적**: [한 줄]
- **트리거**: [언제 쓰는가]
- **커맨드**: /[name]

## 문제 정의
[사용자가 말한 문제를 구조화]

## 입력 / 출력
| 항목 | 내용 |
|------|------|
| 입력 | |
| 출력 | |
| 트리거 | |

## 스킬 경계
- 한다: ...
- 안 한다: ...
- 사람이 판단: ...

## 성공 기준
- [ ] [자동 검증 항목]
- [ ] [수동 확인 항목]

## 레퍼런스
- ...

## 다음 단계
/skill-design 으로 설계 진행
```

---

## 완료 후 안내

```
기획 완료. docs/skill-brief.md 생성됨.

다음: /skill-design 으로 설계 단계를 시작하세요.
설계 전에 기획서를 직접 검토하고 수정하는 것을 권장합니다.
```
