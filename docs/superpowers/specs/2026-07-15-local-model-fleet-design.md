# 로컬 모델 플릿 전략 설계 (Wave AI Networks)

- **작성**: CEO(주인님과 공동 기획) · 2026-07-15
- **상태**: 승인 확정 (§1~§4 + Hermes 보류 판정)
- **목적**: Claude/Codex 토큰 절약을 위해 로컬 LLM을 백그라운드 배치 노동력으로 안전하게 운용

---

## 0. 배경 — 이 설계를 낳은 야간 실전

2026-07-14~15 야간에 로컬 모델을 처음 플릿에 도입하며 두 사고를 겪었고, 그 실전이 이 설계의 하드 제약을 실증했다:
1. **RAM 폭주**: gemma4:31b를 기본 컨텍스트(262144)로 띄우니 RSS 41.6GB·swap 91%·물리 여유 243MB → 시스템 hang 위험(3회 재발).
2. **캡 무력화**: 서버 env(`OLLAMA_CONTEXT_LENGTH=32768`)·Modelfile 변형 둘 다, 클라이언트(Hermes)가 API 호출에서 `num_ctx=262144`를 **명시 override**하면 무력. → "경계에서 강제 못 하면 클라이언트를 신뢰하지 마라" 원칙 재확인.

## 1. 근본 전제 — 로컬은 "느린 무료 비동기 배치 노동력"

- 로컬 모델(gemma4:31b 등)은 CPU/GPU 한계로 **느리다**(한 문장 응답 2분+). 이것은 소프트웨어로 못 고친다.
- 따라서 로컬은 **"빠른 워커"가 아니라 "무료·무한·비동기 배치 노동력"**으로 재정의한다. 속도로 경쟁하지 않고 **밤새 쉬지 않고 도는 것**으로 가치를 낸다.
- 사람이 기다리지 않는 대량·반복 작업에만 투입(밤새 398건 무인 처리 등).

## 2. 플릿 규모 — 시분할 1개 (동시 상주 금지)

- 이 머신은 20GB급 로컬 모델을 **동시 2개 못 돌린다**(gemma4:31b 하나로도 물리 여유 11%·swap 87% 실측).
- **시분할**: 여러 로컬 모델을 등록하되 **한 번에 하나만 메모리 로드**. 안 쓰는 모델은 언로드(ollama keep_alive 관리). 모델 전환 시 콜드로드(수십 초)는 수용(비동기 배치라 무방).
- 소형 모델 동시 상주(gemma4:latest 9.6GB × 2)는 품질 저하로 비채택.

## 3. RAM 안전 규율 (헌장급 — 불가침)

- **모든 로컬 모델 로드는 `num_ctx ≤ 32768` 강제**. 모델 기본값(gemma4:31b=262144) 상속 금지.
- **강제 지점 = 경계**: 서버 env·Modelfile은 클라이언트 override에 무력하므로, 통제 가능한 **호출 코드**(우리가 소유한 파이프라인) 또는 **프록시 게이트웨이 clamp**(num_ctx>32768 요청을 강제 하향)에서 강제한다. 서버 기본값만 믿지 않는다.
- **동시 로컬 모델 1개**(§2). CSO가 RSS·swap 상시 감시, 임계 시 유휴 모델 언로드.
- **CSO 단일 감시자**: 정본 = cmux CSO 하나. cys.app 보조 런타임의 cys-CSO는 감시 전용(시스템 개입 금지·split-brain 방지·90s 폴백).

## 4. 스코프 — 토큰절약 + 백그라운드 배치만 (YAGNI)

로컬이 하는 것(🟢)과 클라우드 전용(🔴)을 못 박는다. 애매한 중간(🟡 콘텐츠 초안 로컬화)은 **지금 배제**(나중에 필요하면 재검토).

| 🟢 로컬(백그라운드 배치) | 🔴 클라우드(Claude/Codex/agy) |
|---|---|
| llm-wiki 속성부여(태그·요약·related) | 검수·판정·전략 |
| 대량 문서 1차 분류·요약(백로그·수집물) | 콘텐츠 저작·신학 정확성·발행물 |
| (선택) 환경스캐닝 원신호 1차 판독 | 주인님 대화·긴급 판단 |

- **로컬 출력은 그대로 안 씀**: 기계검증(mojibake 전수) 필수 + llm-wiki는 CEO 배치별 승격 게이트.
- **애매하면 클라우드**(로컬은 명백히 안전한 것만).

## 5. 엔진 판정 — 통제형 파이프라인이 정본, Hermes 에이전트는 보류

- **정본 엔진 = 젬마 트리아지 파이프라인**(`~/wave-gemma-triage/`, `gemma_client.py`): num_ctx를 **우리가 소유·통제**(32768 bounded). llm-wiki 속성부여를 이미 수행. 스코프(§4)의 실제 작업을 통제 가능하게 처리.
- **Hermes 에이전트(gemma4:31b·qwen3.6) = 보류**: 서드파티 클라이언트라 num_ctx 262144를 명시 override → 우리 캡 무력화·RAM 위협. 현 스코프에서 프록시 인프라를 짓는 것은 과함(YAGNI). 노드 폐쇄 유지.
- **향후 확장 경로**: Hermes의 에이전트(도구 사용) 기능이 실제로 필요해질 때 → **프록시 게이트웨이 clamp**(num_ctx 경계 강제)를 구축한 뒤 재도입. 이 문서가 그 기준.

## 6. 조직 — AI-Tech본부 산하 플랫폼, COO 운영 게이트

- **소유·관리 = AI-Tech본부(플랫폼 HQ)**: 젬마 트리아지 파이프라인(`~/wave-gemma-triage/`) 코드·num_ctx 통제·가드(단일-인스턴스 락)·watch 잡·ollama 위생은 AI-Tech본부가 소유·관리한다(이미 이 파이프라인의 코드 소유자). 로컬 모델 엔진은 **플랫폼 자산**이므로 AI-Tech 산하가 정본.
- **운영 게이트 = COO**: 배치 작업 디스패치·결과 취합·품질 게이트(mojibake 전수·승격 게이트 조율)는 COO 운영 라인. 즉 **AI-Tech가 플랫폼을 운영·유지, COO가 업무 흐름을 게이트**.
- **CSO**: 시스템 감시(RSS·swap·EDEADLK·num_ctx 준수)는 CSO(단일 감시자).
- **이동 없음**: co-location 불필요. 명부 등재 + 디스패치·게이트 프로토콜만.
- 보고선: 로컬 배치 결과 → (AI-Tech 실행) → COO 취합·게이트 → (승격 등 게이트) CEO.
